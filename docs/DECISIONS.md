## 2026-11-26 · Store 판도 모든 드라이브를 알아서 모으기: 사용자 권한 모으기 + 단축키 도우미 startupTask (1.15.0, 사용자 요청)
- 사용자: "Store 판은 인덱서가 없구나. 꼭 있어야하는데", "빠른 찾기 도우미 설치도 안됨", "이게 가장큰 장점인데 꼭 있어야함".
- **찾은 문제**: Store 판(MSIX)에는 색인 서비스가 없고, 서비스에 연결되지 않으면 느린 드라이브 모으기(`SlowCrawler`)도 시작하지 않았다(`OnIndexerStateAsync`가 연결됐을 때만 `StartSlowCrawl`). 그래서 Store 판은 C:는 물론 USB·네트워크 드라이브도 모으지 않고, 무엇이든 찾기는 연 폴더 안만 훑었다. 첫 연결 때 켜던 정리 알림·AI 연결 제안도 나오지 않았다. 단축키 도우미(foldy-hotkey.exe)는 패키지에서 빠져 있었다.
- **고른 길 (세 가지 비교)**:
  | | A. 패키지 서비스 (`desktop6:Service`, SYSTEM) | B. Store에 MSI로 내기 (Win32 제출) | **C. 사용자 권한으로 직접 모으기 (고름)** |
  |---|---|---|---|
  | 속도 | 설치본과 같음 (MFT를 몇 초에 읽음, USN으로 바로 반영) | 설치본과 같음 | 처음 C: 목록에 몇 분, 그다음은 바뀐 폴더만. 켜져 있는 동안 변경 알림으로 바로 반영 |
  | Store 심사 | `localSystemServices`·`packagedServices` 제한 기능. Microsoft 문서가 "대부분 승인되지 않는다". 거절되면 자동 배포의 Store 제출이 멈춘다 | 새 Store 제품(MSI 종류)을 따로 만들어야 하고(지금 제품은 MSIX), 신뢰할 수 있는 인증서로 모든 exe·MSI 서명 필요 (Certum 아직) | 제한 기능 없음 (`runFullTrust`만, 지금과 같음). startupTask는 일반 기능 |
  | 바로 되나 | 승인 여부가 불확실, 검증할 Windows Store 환경 없음 | 인증서 발급 뒤 | 이번 릴리스로 바로 |
- **C를 고른 까닭**: "모든 드라이브 자동 색인, 수작업 설정 없음, 갑작스런 부하 없음"이라는 강점을 지금 바로 Store 판에도 준다. 모으기 코드(`SlowCrawler`: 쉬어 가며 읽기, 끊긴 곳부터 이어서, 폴더 시각으로 바뀐 폴더만, 변경 알림)는 이미 회사 드라이브에서 다듬은 것이라 C:에도 그대로 쓴다. 관리자 권한이 없어 MFT를 읽을 수 없으므로 처음 한 번은 설치본보다 느리다.
- **구현**: `SelfGathers`(= 패키지로 실행 중)이면 `CrawlDrives`가 이 PC의 NTFS 드라이브도 넣고, 서비스에 연결되지 않았을 때 `StartSelfGather`가 모으기·상태 표시(5초마다)·첫 안내를 켠다. 같은 PC에 설치본 서비스가 있어 연결되면 그 서비스가 다루는 드라이브는 빠진다(전과 같음). 상태 줄은 "찾기: 목록 만드는 중 · 몇 개" → "찾기: 준비 끝 · 몇 개", 무엇이든 찾기 아래 줄은 "준비된 드라이브 전체에서 찾아요".
- **단축키 도우미**: MSIX에 foldy-hotkey.exe를 넣고 `desktop:StartupTask`(TaskId FoldyQuickSearchKey, Enabled true)로 로그인 때 띄운다. 패키지 앱은 사용자 Run 값이 패키지 안에 따로 저장돼 쓰이지 않으므로 `SetAutostart`는 Store 판에서 아무것도 하지 않는다. 도우미는 설정 파일에서 단축키·주기 모으기를 모두 끈 것을 보면 바로 끝나므로, startupTask가 켜져 있어도 쓰지 않는 사람에게 남지 않는다. 사용자는 작업 관리자 → 시작 앱에서 끌 수 있다.
- **CI**: Store 패키지는 릴리스 때만 만들어서 매니페스트가 틀리면 늦게 안다 → `build/store/check-msix.ps1`가 가짜 exe로 `make-msix.ps1`을 돌려 makeappx 검사, startupTask가 foldy-hotkey.exe를 가리키는지, 서비스·업데이트 도구가 빠졌는지 본다.
- **나중에**: A안(패키지 서비스)은 심사 사유 글을 [store.md](store.md)에 준비해 두었다. Store 판 사용자가 "처음 준비가 느리다"고 하면 그때 따로 제출해 본다(거절돼도 지금 판은 그대로). 또 관리자 없이 읽을 수 있는 `FSCTL_READ_UNPRIVILEGED_USN_JOURNAL`(Windows 10 1709+)로 꺼져 있던 동안의 변화를 더 싸게 따라가는 방법도 살펴볼 수 있다.

## 2026-11-26 · 왼쪽 메뉴에 Windows 기본 폴더 늘 보이기, 음악은 빼고 동영상은 넣기 (1.14.2, 사용자 요청)
- 사용자: "왼쪽 탐색기 최근폴더에 아래 폴더 추가해줘. 근데 음악 동영상은 많이 사용하지는 조사해서 넣을지 판단해보자." (바탕화면·다운로드·문서·사진·음악·동영상)
- **결정**: "최근 폴더" 제목 바로 아래에 **바탕 화면·다운로드·문서·사진·동영상** 다섯을 늘 보인다(`StandardFolders`, Windows 11 탐색기 홈의 고정 순서). 폴더마다 다른 그림(모니터·아래 화살표·문서·사진·필름), 강조색. 오른쪽 클릭은 새 탭·반대쪽 창. 각 창의 폴더 트리 맨 위도 같은 다섯·같은 순서로 맞췄다.
- **음악은 뺀다, 동영상은 넣는다 (조사)**:
  - Windows 10 빠른 실행은 바탕 화면·다운로드·문서·사진 넷만 고정했고, Windows 11 홈은 음악·동영상까지 여섯을 고정한다. Microsoft도 둘을 "꼭 있어야 할 것"으로 보지 않다가 더한 셈이다.
  - 음악: 음악은 이제 대부분 스트리밍으로 듣는다(IFPI 세계 음악 보고서: 녹음 음악 매출의 약 2/3가 스트리밍, 실물·다운로드는 계속 줄어듦). 음악 폴더에 파일을 모아 두는 사람은 적고, 새로 넣어 주는 Windows 기능도 없다.
  - 동영상: Windows 스스로 여기에 저장한다. 캡처 도구의 화면 녹화는 `동영상\Screen Recordings`, Xbox Game Bar(Win+Alt+R) 녹화는 `동영상\Captures`. 화면 녹화는 할아버지 할머니가 "이거 어떻게 해?"를 보여 줄 때도 쓴다. 저장한 파일을 못 찾는 질문이 Microsoft 질문 게시판에 자주 올라온다.
  - 음악 폴더가 필요한 사람은 핀(자주 쓰는 폴더)으로 고정하면 된다. 목록이 길수록 찾기 어려워서(디자인 원칙: 복잡한 것은 안 하는 게 낫다) 다섯에서 멈춘다.
- **자리는 Windows에 묻는다**: `KnownFolders.PathOf` = `SHGetKnownFolderPath`(KF_FLAG_DONT_VERIFY). OneDrive 백업이 바탕 화면·문서·사진을 `OneDrive\…`로 옮겼거나, 사용자가 다운로드를 D:로 옮겨도 맞다. 전에 트리의 다운로드는 "사용자 폴더\Downloads"를 이어 붙여 옮긴 PC에서 틀렸다. 없는 폴더(지웠거나 회사가 막음)는 빼고, 두 폴더가 같은 자리면(옛 PC: 사진=문서) 하나만.
- **최근 폴더와 겹치지 않게**: 기본 폴더를 열어도 최근 목록에 쌓이지 않는다(쌓이면 다섯 칸 가운데 다운로드·바탕 화면이 늘 자리를 차지한다). 최근 폴더 지우기에도 남는다. quickaccess.json에는 저장하지 않는다(매번 Windows에 묻는다).
- **작은 화면**: 사이드바가 넘치면 먼저 최근 폴더 목록만 접고(기본 폴더 다섯은 남김), 그래도 넘치면 전처럼 "최근 폴더" 묶음 전체를 접는다.
- **다른 안**: 자주 쓰는 폴더(핀)에 처음부터 넣어 두기(기각: 사용자가 지울 수 있게 되면 "어디 갔지?"가 되고, 고정 목록이 처음부터 차 있으면 내 폴더 고정을 알아보기 어렵다), 숨기기 설정(기각: 설정을 늘리지 않는다. 바라는 말이 있으면 그때), 음악도 넣기(기각: 위 조사).
- 시험: StandardFolderTests(최근에 안 쌓임·대소문자·지우기에도 남음·없는/같은 폴더 빼기·그림이 다 다름·음악 없음), KnownFoldersTests(Windows에서 다섯 자리 모두 받고 바탕 화면은 .NET과 같음).

## 2026-11-26 · 무엇이든 찾기 창 옮기기, 주 창도 함께 띄우기 (1.14.2, 사용자 제안)
- 사용자: "Ctrl + space 화면이 고정되어 있는데 옮길 수 있게 해주고, 본창도 같이 뜨게하면 어떨까?"
- **옮기기**: 창 맨 위에 짧은 막대(휴대폰 아래 막대 같은 손잡이, 커서가 이동 모양)를 두고, 그 막대와 글자 칸·단추·결과 목록·미리보기 밖의 빈 곳(위 여백·보기 단추 사이·아래 안내 글)을 끌면 옮겨진다(`DragMove`). 결과 줄은 누르면 열려야 해서 끌기에서 뺐다.
- **자리 기억**: 옮긴 왼쪽 위를 `%LOCALAPPDATA%\Foldy\quick-search-place.txt` 한 줄로 남긴다(`QuickSearchPlace`). 설정 화면·settings.json에 넣지 않았다: 단축키 도우미가 띄운 Foldy와 켜진 Foldy가 바로 같이 읽고, 끌기가 끝날 때 바로 쓴다. 모든 모니터를 합친 넓이에 입력 칸(위 끝 아래 80, 너비 200 이상)이 안 보이면 남긴 자리를 버리고 전처럼 주 모니터 가운데 조금 위에 띄운다(모니터를 떼어 낸 경우).
- **주 창 함께**: 찾기 창을 열 때마다 주 창을 보이게 하고 작게 줄였으면 되돌리고 앞으로 가져온 뒤 그 위에 찾기 창을 띄운다. Foldy가 꺼져 있어 단축키 도우미가 `--quick-search`로 띄운 경우도 같다(1.11.0의 "찾기 창만, 10분 뒤 끝남"은 이제 쓰이지 않는다). 처음 묻는 오류 보고 동의 창은 찾기 창을 닫은 뒤에 묻는다(찾기 창 위로 뜨면 찾기 창이 닫힌다).
- **다른 안**: 켜고 끄는 설정(기각: 사용자가 함께 뜨기를 원했고, 설정을 늘리지 않는다. 불편하다는 말이 있으면 그때 더한다), 찾기 창을 주 창 가운데에 붙이기(기각: 옮긴 자리를 기억하는 쪽이 사용자 말에 맞다), 모니터마다 작업 영역 확인(기각: 주 창과 같은 방식인 가상 화면 넓이로 충분).
- 버전: 새 기능이지만 사용자 결정으로 1.14.2 ("1.14.2로 병합해서 진행하자"). 왼쪽 탐색기 자주 쓰는 폴더 작업과 한 번에 낸다.
- 시험: QuickSearchTests(자리 읽기·쓰기·화면 밖 판단), FlaUI QuickSearchOnlyTests(도우미로 띄우면 주 창도 뜸, 손잡이를 끌면 옮겨지고 다시 열면 그 자리).

## 2026-11-26 · CodeQL이 실패하면 한 번 저절로 다시 돌리기 (사용자 요청)
- **결정**: `rerun-codeql.yml`이 CodeQL 실행이 처음 실패했을 때만 실패한 작업을 한 번 다시 돌린다. 두 번째 실패는 그대로 둔다.
- **왜**: PR 104에서 세 언어 분석이 결과 올리기 단계에서 오류 줄 없이 실패했고(같은 시각 main은 통과, 다시 돌리니 통과), 지켜보던 Claude가 실행이 끝나기 전 다시 돌리기에 실패한 뒤 끝난 실행을 다시 확인하지 않아 7시간 동안 멈춰 있었다. 사용자 "에러 발생하면 자동 조치할텐데 왜 자동조치 안되었는지 확인하고 조치하자".
- **지키는 것**: 코드를 받아 오지 않고 API만 부른다(권한은 actions: write 하나). 앱 빌드·시험(ci.yml)은 저절로 다시 돌리지 않는다: 진짜 실패를 가릴 수 있어서, 지켜보는 Claude가 원인을 보고 고친다. 지켜보는 쪽은 다시 확인할 때를 꼭 예약해 둔다.

## 2026-11-25 · 끌어 놓기 안내는 커서 바로 아래에 (사용자 원칙 "액션하는 위치에 메세지")

## 2026-11-23 · 색인 없는 드라이브 분석은 모아 둔 목록으로 (1.7.3, 사용자 제보)
- **경위**: "K 드라이브 분석을 시켰더니 폴더 읽는 중으로 나온다. 색인은 완료되었다는데…" K:(회사 보안 드라이브)는 색인 서비스(NTFS MFT)가 다루지 않아 SlowCrawler가 목록을 모은다(사이드바 "색인 완료"). 그런데 분석(`AnalysisCoordinator`)은 서비스가 없으면 곧장 `FallbackScanner`로 드라이브를 처음부터 다시 읽었다. 두 기능이 목록을 나눠 쓰지 않았다.
- **결정**: 서비스가 못 하는 드라이브는 SlowCrawler가 **다 모은 목록**(+ 변경 알림으로 더하고 뺀 것)이 있으면 그것으로 스냅샷을 만든다(`CrawledListSnapshot`, `CrawlStore.ReadAll`). 목록이 얼마나 오래됐든 쓴다: 앱이 켜져 있으면 1시간마다 바뀐 폴더만 다시 모으고 변경 알림도 받으므로 대개 최신이고, 오래된 목록이라도 느린 드라이브를 처음부터 다시 읽는 것보다 낫다. 대신 진행 글에 몇 분 전 목록인지, 결과에 "모아 둔 목록"이라고 보이고, 분석한 때는 목록을 다 모은 때로 적는다.
- **쓰지 않는 것**: 모으는 중인 목록(.part)은 반쪽이라 크기가 작게 보이므로 쓰지 않는다. 그때는 예전처럼 직접 읽되, 읽은 폴더·파일 수와 지난 시간, 지난 분석의 파일 수 대비 어림 진행률을 보인다.
- **차이**: 목록은 숨김·시스템 파일을 건너뛰고(SlowCrawler 규칙) 할당 크기를 모르므로 드라이브의 클러스터 크기로 올림한다. 이번에 직접 읽기도 4KB 고정 대신 실제 클러스터 크기(GetDiskFreeSpaceW)로 셈한다(FAT/exFAT은 32~128KB가 흔하다).
- **다른 안**: 분석할 때 목록이 오래됐으면(예: 하루) 직접 읽기 — 느린 드라이브에서 바로 그 불편이 다시 생겨 기각. 분석 전에 SlowCrawler 한 번 더 돌리기 — 바뀐 폴더만 읽어도 회사 드라이브는 수 분이 걸려 기각(사용자가 [다시 분석]을 누르면 그때의 목록을 쓴다). 스냅샷 DB 스키마에 출처 칸 추가 — 서비스(Rust)와 스키마 버전을 같이 올려야 해 기각, 옆에 `.list` 표시 파일을 둔다.

## 2026-11-22 · Foldy가 띄운 창을 닫으면 Foldy 창을 앞으로 (1.2.1, 사용자 제보)
- **경위**: "잠김메모를 저장하고 닫으면 Foldy 창이 내려가서 안보인다." Windows는 주인(Owner)이 있는 창이 닫힐 때 주인이 아닌 z 순서의 다음 창(다른 프로그램)을 앞으로 올리기도 한다. 잠긴 메모는 안내 창(암호)이 먼저 닫히고 메모 창이 열리는 흐름이라 특히 잘 생겼다.
- **결정**: 메모 창 하나만 고치지 않고, 앱 전체에서 주인이 있는 모든 창이 닫히기 직전(아직 보일 때) 주인 창을 먼저 앞으로 올린다(`OwnerFocus`, Window.Loaded 클래스 처리기로 모든 창에). 금고·안내·설정·AI 연결 창도 같은 문제를 가질 수 있어서다.
- **하지 않는 경우**: 닫히는 창이 활성 창이 아닐 때(5분 뒤 저절로 잠기는 메모, 다른 앱을 연 뒤 닫히는 창), 주인 창을 최소화해 뒀을 때, 닫기가 취소됐을 때. 다른 프로그램을 쓰는 사람 앞으로 Foldy를 끌어오지 않게.
- 자동 테스트(FlaUI): 새 잠긴 메모를 만들고 [잠그고 닫기] → Foldy 주 창이 맨 앞인지.

- **특정 보안 제품의 표시는 찾지 않는다**(회사 정보 규칙, docs/no-company-info.md): 제품마다 다른 머리 대신 "형식이 다르고 암호문 같다"로 본다. 화면 문구도 "DRM"·"문서 보안"만 쓴다.
- 클라우드 전용 파일은 검사하지 않는다(내용을 읽으면 내려받기가 시작된다). 새 상태 `PreviewStatus.Protected`.
- **다른 안**: 처리기가 실패한 뒤에만 살피기 → 처리기가 자기 창에 오류를 그리고 실패를 알리지 않는 경우가 있어 앞에서 본다.
- **실제 확인**: 사용자가 회사 PC의 실제 DRM 파일에서 "DRM으로 보호된 파일이라 미리 볼 수 없어요"가 나오는 것을 확인했다 (1.0.1, 2026-11-22).

- **3) 개발 캐시 정리**: npm·NuGet·pip·Yarn·pnpm·Docker 빌드 캐시. 깔린 도구만, **공식 명령만**(폴더를 직접 지우지 않음), 다시 받을 수 있는 것만. Docker는 `builder prune`만(이미지·컨테이너·볼륨 안 건드림). 되살릴 수 없으니 크기를 보여 주고 한 번 확인.
- **넣지 않기로 한 것**: 레지스트리 청소, 텔레메트리·서비스·Windows 업데이트 끄기 같은 최적화 트윅, UWP 앱 삭제, 브라우저 프로필 정리, 잠긴 파일 핸들 강제로 끊기, 환경 변수·hosts 자체 편집기, 심볼릭 링크 만들기. 파일 관리와 상관없거나 되돌리기 어렵고, 회사 PC 보안 정책과 부딪힌다.

## 2026-11-20 · 색인 연결 회귀 (0.9.4)
- **경위**: 사용자가 빠른 검색에서 파일명에 들어 있는 낱말로 찾았는데 못 찾았다. 로그에 "색인 서비스에 연결하지 못함 (서비스 상태: Running)"이 계속 찍혔다. 보안 리뷰 L3로 넣은 "파이프 상대가 SYSTEM인가" 검사가, 보통 권한(중간 무결성)의 Foldy에서는 SYSTEM 프로세스를 열 수 없어(OpenProcess 거부) 진짜 서비스까지 거절했다. 그래서 빠른 검색과 Ctrl+F가 지금 폴더만 훑었다. CI는 관리자 권한으로 돌아 이 경우를 못 잡았다.
- **결정**: 서비스 관리자(SCM)에게 FoldyIndexer 서비스의 프로세스 번호를 물어 파이프 상대가 그 프로세스면 믿는다(보통 권한으로도 물을 수 있고, 서비스 등록은 관리자만 바꿀 수 있어 흉내 낼 수 없다). 그다음 기존 계정 검사(SYSTEM·나 자신). 서비스가 돌고 있는 PC에서는 실제로 연결되는지 테스트한다(서비스 없는 CI에서는 건너뜀). 색인에 연결되지 않으면 빠른 검색 아래에 ⚠로 "지금 폴더 안에서만 찾아요"를 분명히 보인다.
- **교훈**: 권한에 따라 갈리는 검사는 관리자·보통 권한 둘 다에서 확인한다. 개발 PC 수동 점검 M13으로 남긴다.

## 2026-11-20 · 빠른 검색 (Ctrl+Space, 사용자 요청·기능 동결 예외)
- **결정**: macOS Spotlight처럼 어디서든 Ctrl+Space로 화면 가운데 큰 검색 칸을 연다. 한 칸에서 찾는 것: Foldy 기능(명령), 파일·폴더(색인 DB, 색인이 없으면 지금 폴더 안), 앱(시작 메뉴 바로 가기), Windows 설정 항목(ms-settings:), 자주 쓰는/최근 폴더(위쪽에), 간단 계산·단위 변환(입력하면 바로 결과, Enter로 복사). 결과는 종류별 묶음, 맨 위에 "가장 알맞은 것" 하나, 오른쪽에 미리보기. Enter 열기·실행, Ctrl+Enter 들어 있는 폴더 보기, Esc·바깥 누르면 닫기. 기능은 띄어 쓴 낱말·초성(ㅅㅈ → 설정)으로도 찾는다.
- **말하듯 찾기·공통 기능 (사용자 요청, "복잡하면 하지 말고")**: 메모 쓰기·정리 도구·금고·설정 같은 Foldy 기능은 모두 명령 목록 한 곳에 등록돼 있어 빠른 검색에 저절로 나온다(새 기능도 등록만 하면 됨). "다운로드 정리해줘", "메모 쓸래"처럼 말하듯 쳐도 끝말을 다듬고(해줘·할래·쓸래 → 쓰기…) 기능마다 붙인 쉬운 말(QuickIntent.Keywords)로 맞춘다. 문장으로 물으면 "이걸 할까요? Enter를 누르면 시작해요"로 대답하고, Enter면 그 기능의 **기존 대화 창**이 이어서 한 단계씩 묻는다. 외부 AI나 전송은 쓰지 않는다.
- **하지 않은 것 (복잡해서)**: 검색 창 안에서 여러 단계 대화를 새로 만드는 것. 정리 도구들이 이미 대화 창으로 한 단계씩 묻기 때문에 그것을 그대로 쓰는 쪽이 단순하다. Ctrl+Space를 "Foldy에게 말 걸기" 하나의 입구로 삼아 첫 화면 버튼을 줄이는 것은 써 본 뒤 사용자 동의를 받고 정한다.
- **넣지 않은 것**: 웹 검색·사전(밖으로 아무것도 보내지 않는다). 태그·메모 내용·SFTP·Git 검색은 써 보고 정한다.
- **단축키 겹침**: 전역 단축키(RegisterHotKey)로 등록한다. 다른 프로그램이 이미 쓰거나, 중국어·일본어 입력기가 설치돼 있으면(Ctrl+Space가 입력 전환 키) 겹친다고 본다. 겹치면 조용히 넘어가지 않고 알리고, 비어 있는 키 후보(Ctrl+Shift+Space, Ctrl+Alt+Space, Ctrl+Alt+F, Win+Shift+F 중 실제로 비어 있는 것)와 [직접 눌러서 정하기], [Foldy 안에서만 쓰기]를 보여 준다. 확인은 처음 설정(글자 크기·밝기 다음)에서 하고, 업데이트 때는 묻지 않고 등록만 하다가 실패할 때만 알린다. 설정 → 단축키에서 언제든 바꾼다. 시험용 실행(FOLDY_DATA_DIR)에서는 등록하지 않는다.
- **찾기 장면: 냄새 잘 맡는 블러드하운드 (사용자 결정)**: 파일을 찾으면 축 늘어진 귀와 이마 주름의 블러드하운드가 코를 바닥에 대고 킁킁 → 귀를 펄럭이며 쌩 달려가 → 폴더를 물고 꼬리를 흔드는 0.5초 장면과 "킁킁! 0.03초 만에 1,284개 물어 왔어요"를 보인다. 못 찾으면 고개를 갸웃한다. Foldy 고유의 단순한 도형 그림(특정 캐릭터 아님), 대사는 한 곳(나중에 리소스)에. 애니메이션은 Windows 애니메이션 설정이 아니라 Foldy 설정의 "애니메이션 사용"을 따른다(농구 애니메이션과 같음).
- **처음 안("엄마 찬스")을 바꾼 이유**: "엄마는 뭐든 다 해 준다"는 고정관념을 담을 수 있고 엄마의 수고를 가볍게 다룬다는 의견이 있었다. 냄새로 찾는 개는 어느 문화에서나 "잘 찾는다"로 바로 읽히고 누구의 역할도 정하지 않는다.
- **다른 안**: Foldy 창 안에서만 여는 단축키 — 사용자가 "macOS처럼"을 원해 전역으로. 끄고 싶으면 [Foldy 안에서만 쓰기].

## 2026-11-20 · 빨리 지우기 (사용자 요청·기능 동결 예외)
- **결정**: 지우려는 곳에 파일이 **5,000개 이상**이면 지우기 전에 대화 창으로 묻는다. [휴지통으로 (되살릴 수 있어요)]가 기본, [빨리 지우기]를 고르면 "휴지통에도 남지 않아 되살릴 수 없어요, 중간에 멈춰도 이미 지운 것은 돌아오지 않아요"를 한 번 더 알리고, 그 확인의 기본 단추는 [그만두기]다(Enter 실수 방지). Shift+Delete(영구 삭제)로 지울 때도 같은 창이 나온다.
- **왜 5,000개**: Windows 휴지통은 파일 수천 개부터 눈에 띄게 느려지고(목록을 휴지통 데이터베이스에 하나씩 기록), 그보다 적으면 묻는 창이 오히려 방해가 된다. 세는 데는 2초까지만 쓰고, 다 못 세면 "○개 넘게"로 보인다.
- **방법**: 외부 명령(robocopy·rd) 없이 Foldy가 직접 병렬로 지운다. 폴더마다 안의 파일을 여러 스레드로 지우고(로컬 드라이브는 CPU 수×2, 최대 16), 비면 가장 깊은 폴더부터 지운다. 네트워크 드라이브는 동시에 4개만(회사 보안 드라이브 같은 느린 곳도 무리하지 않게). 읽기 전용·숨김·시스템 속성은 풀고 지운다. 긴 경로(260자 넘음)도 지운다. 정션·심볼릭 링크는 **링크만 지우고 안으로 들어가지 않는다**(다른 곳의 원본 보호). 작업 창에 지운 개수가 보이고 언제든 [취소]할 수 있다.
- **지우지 않는 곳**: 드라이브 맨 위, Windows, Program Files, ProgramData, 사용자 폴더 자체, 바탕화면·문서 폴더 자체는 빨리 지우기를 거절한다(휴지통으로만).
- **구현 위치**: 처음에는 Rust 엔진 안에서 하려 했으나, 하는 일이 "파일 하나씩 DeleteFileW"라 C#(.NET 파일 API = 같은 Win32 호출)으로 Foldy.Core에 두었다. 같은 병렬 방식이고 테스트(링크 보호·긴 경로·취소·보호 경로)를 쉽게 붙일 수 있다. 엔진 경계(FFI)를 늘리지 않는다.
- **애니메이션**: 영구 삭제와 같은 "경기장 밖" 장면.

## 2026-11-24 · Foldy가 꺼져 있어도 Ctrl+Space로 찾기 (1.11.0, 사용자 요청)
- **경위**: 사용자(2026-11-24) "Foldy가 실행 안되어 있어도 ctrl + space 키를 누르면 foldy 검색창이 뜨도록". 지금은 Foldy 창이 켜져 있어야 전역 단축키가 등록된다.
- **결정**: 아주 작은 단축키 도우미 `foldy-hotkey.exe`(Rust, engine/foldy-hotkey)를 둔다. 로그인할 때 시작해 키 하나만 기다린다. 창·아이콘·다른 라이브러리 없이 Win32 함수만 써서 메모리 약 1MB.
  - 누르면: Foldy가 켜져 있으면 단일 인스턴스 파이프로 `--quick-search`를 보내 찾기 창만 연다(주 창은 그대로). 꺼져 있으면 같은 폴더의 `Foldy.exe --quick-search`를 띄운다. 이 Foldy는 주 창을 띄우지 않고(Show 안 함) 찾기 창만 연다. 색인 서비스 연결은 0.7초까지 기다려 처음부터 모든 드라이브에서 찾는다.
  - 찾기 창만 떠 있는 Foldy에서: 파일은 그 파일의 프로그램으로만 열고, 폴더·Foldy 기능·"Foldy에서 보기"·마크다운·잠긴 파일처럼 Foldy 창이 필요한 것을 고르면 그때 주 창을 처음 띄운다. 찾기 창을 닫고 10분 동안 다시 쓰지 않으면 끝나 메모리를 돌려준다(그동안은 다시 누르면 바로 뜸). 정리 알림·AI 제안은 주 창이 보일 때로 미룬다. 창 위치·탭은 저장하지 않는다(바뀐 게 없음).
  - 키는 Foldy가 정한다: Foldy가 켜질 때(그리고 설정을 바꿀 때) 도우미를 잠깐 끄고, 예전 흐름대로 키를 확인한다(입력기·다른 프로그램과 겹치면 알리고 다른 키 고르기). 확인한 키를 `%LOCALAPPDATA%\Foldy\quick-search-key.txt`에 `수식 키 비트 가상 키` 숫자로 적고 도우미를 다시 띄운다. 둘이 같은 키를 등록할 수 없으므로 도우미가 쥐고 있는 동안 Foldy는 키를 등록하지 않는다. 도우미가 뜨지 못하면(다른 프로그램이 키를 씀 등) 예전처럼 Foldy가 켜져 있는 동안만 받는다.
  - 설정 파일이 없으면(설치 뒤 Foldy를 한 번도 안 켬) 기본 Ctrl+Space. 단, 중국어·일본어 키보드가 있으면 Ctrl+Space가 입력기 전환 키라 도우미는 키를 잡지 않고 끝난다(Foldy를 켜면 다른 키를 고르게 묻는다). 한국어 입력기는 한/영 키라 겹치지 않는다.
  - 켜고 끄기: 설정 → 일반 → 빠른 찾기 "Foldy가 꺼져 있어도 단축키로 찾기 창 열기"(기본 켬, `QuickSearchAlways`). 끄면 설정 파일에 `off`를 적고 도우미를 끈다. 로그인 때 떠도 `off`를 보고 바로 끝난다. "다른 프로그램에서도 받기"(`QuickSearchGlobal`)를 끄면 함께 쉰다.
  - 로그인 시작: MSI가 HKLM Run `Foldy Quick Search`에 넣는다(모든 사용자, 제거하면 지워짐). 압축 파일 설치처럼 HKLM 값이 없으면 Foldy가 HKCU Run에 넣는다. 설치·업데이트·제거 때 MSI가 도우미를 끝낸다(사용자 권한으로 한 번, 다른 사용자 것까지 관리자 권한 taskkill로 한 번). 업데이트 뒤에는 Foldy를 켜거나 다시 로그인할 때 다시 뜬다.
  - Store 판(MSIX)에는 넣지 않는다: Store 인증 중이고 시작 작업(startupTask)은 따로 확인이 필요하다. Store 판은 예전처럼 Foldy가 켜져 있을 때만.
- **함께 고친 것**: 단일 인스턴스 이름의 사용자 부분이 `string.GetHashCode`였는데, .NET은 이 값을 프로세스마다 다르게 섞는다. 그래서 Foldy를 두 번 켜면 두 번째가 첫 번째를 찾지 못해 창이 둘 뜰 수 있었다. 사용자 이름의 FNV-1a 32비트(대문자 UTF-8)로 바꿨다. 도우미도 같은 규칙으로 파이프 이름을 만든다(양쪽 시험에 같은 값).
- **왜 이 방식**: 색인 서비스(SYSTEM, 세션 0)는 사용자 화면의 키를 받을 수 없다. Foldy 전체를 로그인 때 숨겨서 띄우면 늘 수십~백 MB를 쓴다(메모리 작은 PC). 키보드 훅(SetWindowsHookEx)은 모든 키 입력을 보게 되어 보안 프로그램이 의심하고 부담도 크다. RegisterHotKey 하나만 쓰는 작은 도우미가 가장 가볍고 안전하다. 첫 번째 누름은 Foldy가 뜨는 1~2초가 걸리는 대신 메모리를 아낀다.
- **다른 안**: Foldy를 트레이에 늘 띄워 두기(메모리), 서비스가 키 받기(세션 0이라 불가), 도우미가 처음부터 찾기 창을 직접 그리기(찾기 창·색인 연결을 두 번 만들어야 해 기각), 찾기 창만 쓴 Foldy를 바로 끝내기(연달아 찾을 때마다 1~2초, 10분 남기기로 절충).
- **시험**: Rust `foldy-hotkey` 단위 시험(설정 읽기, 입력기 판정, 사용자 이름 해시, 파이프 요청 형식). Foldy.Platform.Tests(해시가 도우미와 같은지, 설정 줄·Run 값 형식). Foldy.Interop.Tests `QuickSearchKeyAgentTests`(진짜 도우미를 띄우고 Ctrl+Alt+Shift+F24를 눌러 켜져 있는 Foldy 파이프에 `--quick-search`가 가는지, off면 바로 끝나는지, 하나만 뜨는지, Foldy가 끄라고 하면 끝나는지). Foldy.UiTests `QuickSearchOnlyTests`(`--quick-search`로 띄우면 찾기 창만 뜨고 주 창은 없음, 계산이 되고, 그 뒤 Foldy를 켜면 같은 프로세스가 주 창을 띄우고, 주 창이 있을 때 `--quick-search`는 찾기 창만).
